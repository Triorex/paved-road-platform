Paved Road

An end-to-end secure software supply chain on GitHub Actions, built so that one central set of reusable workflows protects a fleet of about 80 repositories, from the developer's laptop to production.

§2

Problem and design principles

The starting point this design fixes

  • Each team runs its own pipeline, so security coverage differs from repo to repo and often happens after development.
  • Builds pull packages straight from public registries, so nothing stops a malicious or typosquatted package.
  • No one can prove where a production image came from, or that it passed the required checks.
  • Findings pile up in separate tools with no owner and no deadline, so the backlog only grows.
  • Pipelines themselves hold long-lived cloud keys and unpinned third-party actions.

What success looks like

  • Every repo in the fleet runs the same versioned security gates, with no opt-out.
  • Open source enters through one curated front door.
  • Every production image carries an SBOM, a signature and build provenance, and the cluster checks them.
  • Every finding has an owner, an SLA and a closure confirmed by rescan.
  • Pipelines use short-lived OIDC credentials and pinned actions only.
Paved road, not toll booths
The secure path is the easiest path. A team gets every control by calling one workflow.
Shift left, verify right
Catch issues on the laptop and in the PR; prove integrity again at deploy.
Guardrails before gates
New rules start in audit mode, get tuned for false positives, then enforce.
One front door for open source
Packages and base images come only through curated sources.
Provenance by default
Every artifact is signed and attested. Unsigned means undeployable.
Central, versioned, self-service
Platform owns the logic; app teams consume it by pinned version.
Measure adoption, not activity
Coverage, time to fix and share of production on the paved road.

Each control lists what stops the flow and where it lives. Blocking is reserved for high-confidence, high-impact findings. §4

How the cluster knows an image came through the paved road

This is why reusable workflows beat composite actions here. A reusable workflow owns its whole job, including the runner and token permissions, and its name appears in the OIDC token. A composite action runs inside the caller's job, so the caller could change what happens around it.

§8

Build procedure

The order protects the core path. If time runs short, later items stay as finished files without a live run, and the coverage matrix in the repo says so.

  1. Setup

    • Create the project folder and the three local repositories.
    • Install kind, cosign, syft, trivy and helm with Homebrew. Start Docker Desktop.
    • Create the triorex GitHub organization and log in with gh auth login (scopes: admin:org, workflow, write:packages).
    • Write the approved plan into docs/PLAN.md and open VS Code.

  2. Platform repo

    • Security config: policy thresholds, exceptions, Semgrep rules, license allowlist, ZAP rules.
    • Reusable workflows: pr-security.yml, secure-build.yml, release.yml, staging-verify.yml.
    • Kyverno policies and the scripts: curation, exceptions, triage, demo, verify.

  3. Consumer repos

    • payments-api: FastAPI service, tests, hash-pinned requirements, Chainguard Dockerfile, caller workflow.
    • orders-api: Express service, Jest tests, lockfile, Chainguard Dockerfile, caller workflow.

  4. Publish

    • Create the public repos in the org and push (platform and payments-api; orders-api next).
    • Apply governance: secret scanning with push protection, Dependabot, branch rules, environments, allowed-actions policy.

  5. First green run

    • Open a PR and watch every gate pass. Merge to build, scan, generate the SBOM, sign and attest; promote to staging, then run admission and DAST against the deployed workload.
    • Check the result with cosign verify and gh attestation verify.

  6. Admission

    • CI: staging verify admits the signed image and denies unsigned and privileged ones, before ZAP runs.
    • Laptop: the same demo on a local kind cluster.

  7. Release and operate

    • Promote dev → staging → production: QA signs off in staging, appsec approves production, with DAST and QA evidence and forward-only checks; the GitHub Release is recorded only after production.
    • Developers deploy any branch to dev with Run workflow; branch builds never go further.
    • Ship platform changes as -rc.N, prove them in ring 0, then promote to final.
    • Run triage, Scorecard, fleet onboarding (live on payments-api, dry-run on 78) and the compliance report.

  8. Docs and walkthrough

    • Design document, threat model, plan and ADRs.
    • Walk through a live pipeline run and make demo.

Demo pull requests

  1. Add a known-vulnerable package: dependency review and OSV block it.
  2. Add a SQL injection: CodeQL and Semgrep flag it.
  3. Hardcode a test secret: gitleaks blocks it.
  4. Make the pod privileged: the Kyverno CLI blocks the manifest.

What you need from the GitHub side

  • The triorex organization.
  • Public repos, so GHAS code scanning, secret scanning and dependency review run at no cost.
  • GHCR packages set to public, or pull credentials added to the local kind cluster.

§11

Branching and scale

Decision: trunk-based development with build-once promotion. Branches are code lines; environments are deployment targets. One signed digest moves through dev, staging and production, so what QA approved is byte-for-byte what ships. Environment branches (dev, staging and prod branches promoted by merges) were considered and rejected.

Environment branches offerWhy that hurtsHow this design gets the same benefit
A review at every promotionThe promotion PR re-reviews a diff already reviewed on the feature PR, so it becomes a rubber stampCode review on the feature PR; QA and appsec approvals on the same digest, with signed evidence
A prod branch that shows what is liveEach merge makes a new commit, a new build and a new digest: production would ship an artifact QA and DAST never tested, and the signed evidence would not matchThe production image tag, the GitHub Release recorded after each production deploy, and (planned) a production git ref the pipeline fast-forwards
Staging can hold a release while dev moves onBranches drift; every hotfix must be back-merged; merge conflicts growShort release branches (release/x.y) only when a release must stabilise, still built once and promoted
A hotfix lane from productionMain lags behind production, so developers branch from stale codeBranch from the production release, PR to main, same pipeline

Many developers on one repository

What breaks firstEffectPlanStatus
One shared dev environmentBranch deploys overwrite each other: last deploy winsA preview environment per branch (dev-<branch> namespace), created on deploy and removed when the PR closes; shared dev tracks mainDesign
Approval fatigueEvery merge asks for a QA and a production approvalApprove the newest build only: it contains every earlier merge, a natural release train. Older waiting runs are cancelled; forward-only promotion would refuse them anywayDesign
PRs green alone, broken togetherTwo PRs pass separately but conflict once both land on mainA merge queue tests each PR on top of everything ahead of itDesign
Review rulesThe demo requires no approving review (single maintainer)One or more approvals, required code-owner review, no self-approvalDesign
Older build overtaking a newer oneA slow run promoted after a faster one would roll an environment backForward-only promotion and one promotion per environment at a timeLive

At enterprise scale in a regulated organisation

AreaWhat this design would add
EnvironmentsMore than three (dev, SIT, UAT, performance, pre-production), all promoting the same signed artifact
Change managementThe pipeline opens and closes change records in the ITSM tool. Risk-based approval: low-risk changes with complete evidence go through as standard changes; high-risk ones go to a change advisory board
Release coordinationRelease trains or short release branches, freeze windows, cross-service dependencies
Production rolloutProgressive delivery: canary or blue/green, feature flags, automated rollback on error rates
Developer throughputMerge queues, per-branch preview environments, monorepo or polyrepo tooling, a platform team running the paved road
Legacy systemsMainframe and vendor systems often keep release branches and slower cycles; the paved road covers modern services first
AuditEvidence retained for years, tamper-evident and searchable per release, not only in CI logs

This implementation is a reference for the core pattern (one trunk, build once, promote a signed artifact, approvals backed by evidence). The items marked Design and the enterprise additions are the next layers, not claims about what runs today.
